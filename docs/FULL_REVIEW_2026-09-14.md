# 전체 소스 검토 — 2026-09-14

## 판단

주요 생산 경로를 설비 동작·정지·재개·결과 귀속 기준으로 검토했다. 유닛별 시퀀스, 장치 호출, 공통 I/O·모션 경계는 현재 구성을 유지해도 된다. 이번에 확인된 우선 수정 대상은 **완료 신호를 과거 이력으로 받아들이는 경로**와 **볼트 티칭이 없는 소재의 작업 완료 처리**였다. 둘 다 수정 전 가상 테스트로 재현하고 수정했다.

전체 파일의 무결성이나 실장비 적합성을 보증하는 검토는 아니다. 제조사 SDK 원본을 전부 재검증하지 않았고 실장비 동작·통신·UI 조작은 수행하지 않았다.

## 수정 1 — 실린더 완료 신호의 현재 상태 확인

위치: `Shared/IBTM.Device/IIoService.cs`, `WaitForInputsAsync`.

수정 전에는 기대 센서 ON·반대 센서 OFF가 한 번 확인되면 Task가 완료됐다. 시퀀스가 이어지기 전에 기대 센서가 다시 OFF가 되거나 반대 센서도 ON이 되어도 성공을 반환했다. 두 경우를 실행 순서를 고정한 테스트에서 재현했다.

기존 공통 이벤트 대기를 사용해, 액추에이터 완료는 반환 직전 센서 쌍을 다시 확인한다. 조건이 사라졌으면 처음 정한 제한 시간 내에서 계속 기다리며 출력 명령을 재전송하지 않는다. 볼트 통과 등의 단일 입력 대기는 짧은 펄스를 계속 기억한다. 별도 감시 루프나 안정화 시간 설정은 추가하지 않았다.

## 수정 2 — 볼트 티칭 누락을 작업 완료로 처리하지 않음

위치:

- `IBTM/MachineController.Automatic.cs`, `TeachingReady`.
- `Stations/IBTM.BoltFastening/BoltFasteningStation.cs`, `RunCarrierAsync`.
- `Stations/IBTM.Inspection/InspectionStation.cs`, `ExecuteInspectionAsync`.

수정 전에는 HS1 볼트만 등록하고 HS2가 들어오면 HS2의 작업 목록이 비어 있어 체결·검사 모두 완료됐다. 실제 자동 시작 경로를 사용하는 가상 테스트에서 두 유닛의 `work.Completed == true`를 확인했다. 검사만 사용하는 경우에는 Data Matrix FOV만 등록해도 볼트 목록이 없는 레시피를 준비 완료로 판단했다.

이제 활성 체결·검사 유닛은 최소 한 개의 볼트 티칭을 요구한다. 소재가 안착하면 이번 작업 대상 히트싱크 각각에 볼트가 등록되어 있는지 확인하고, 없으면 대상 이름을 포함한 알람으로 정지한다. 완료나 OK 결과를 만들지 않는다. 해당 유닛을 비활성화한 이송 운전에는 이 조건을 적용하지 않는다.

`BufferStage` 등의 이름은 남아 있지만 현재 역할은 두 핸들러의 인계·간섭 구역 확인이다. 물리 버퍼의 내려놓기 동작을 다시 추가할 이유는 없다. 이름 일괄 변경이나 유닛 시퀀스의 추가 공통화는 이번 결함 해결에 필요하지 않아 수행하지 않았다.

## 추가 검토 — 레시피 교체 후 복구 확인 갱신

위치: `IBTM/UI/StartPreparation.cs`와 Placement·Fastening 복구 준비 클래스.

작업자가 재시작할 작업을 확인한 뒤 레시피를 다시 불러오거나 새로 만들면, 센서 변화가 없는 한 이전 확인이 그대로 유효했다. 기존 복구 창 테스트에 저장·로드 경로를 연결해 수정 전 `Prepared == true`가 남는 것을 재현했다.

기존 `RecipeEditor.Changed` 이벤트를 복구 확인 무효화에 연결했다. 불러오기 성공·새 레시피 생성 후에는 Placement와 Fastening 모두 다시 확인한다. 저장 또는 불러오기 실패만으로 확인을 취소하지 않는다. 캐리어 작업 ID와 실제 작업 결과는 보존하며, 이 변경이 결과를 새 레시피에 맞게 자동 변환하거나 재체결 여부를 판단하지는 않는다.

직접 관련 Virtual 테스트 8개 통과: 실제 복구 창을 포함한 기존 UI 테스트 1, 저장·로드 작업 수명 1, 잘못된 검사 레시피 로드 3, 중단된 체결 결과 귀속 3. UI 테스트에서 저장 직후 표시 상태를 즉시 검사하던 한 곳은 기존 비동기 표시 갱신을 기다리도록 수정했다. 실장비 앱이나 네이티브 하드웨어 API는 실행하지 않았고 전체 MachineFlow도 실행하지 않았다.

## 추가 검토 — 일상 조작과 운전 중 정지 원인

조그·스텝·원점복귀, 정지·RESET, Supply 직접 인계, Placement 압착 완료, Main Conveyor 안착·배출, 볼트 피더·체결 결과 수집, 검사 취소, NG 배출·Repeat 복귀를 소스에서 이어서 대조했다. 드문 레시피 변경보다 일상적인 조작과 정지 시 원인 확인을 우선했다.

### 이동 거절이 처리되지 않은 UI 예외로 전파되는 문제

조그 명령이 제어권을 얻은 직후 실린더 상승 피드백이 사라지면, Placement와 Inspection 모두 축을 움직이지는 않지만 `InvalidOperationException`이 UI 명령 밖으로 전파됐다. 명령 시작 시점에 신호를 바꾸는 가상 테스트 두 건으로 재현했다.

현재 설비 상태에 따른 이동 거절은 `MotionInterlockException`으로 구분해 기존 수동 명령 오류 처리에서 해당 유닛 알람으로 표시한다. 실린더 상승, 인계 구역, Z 높이·원점, 축 정지·InPosition 확인에 적용했다. 잘못된 축 등 프로그래밍 오류는 기존 구분을 유지한다. 새로운 감시 루프나 상태 캐시는 추가하지 않았다.

### 운전 중 인터록 정지의 상세 원인

기존 `CheckMotionInterlocks`는 유닛 이름만 알람에 남겼다. 이제 Placement 리프트, Pickup/Shooting 헤드, Inspection/NG 픽업의 필요한 조건과 현재 피드백 상태를 함께 남긴다. 정지 조건과 STOP 순서는 유지한다.

직접 관련 Virtual 테스트는 중복을 제외한 **26개 통과**. 이동 거절 수정 후 23개, 알람 상세 보강 후 관련 7개를 실행했으며 이 중 4개가 겹친다. 재현 테스트 두 건 외에는 기존 안전·재개 테스트의 기대 예외와 알람 상세를 보강했다. 전체 MachineFlow와 실장비 앱 실행은 하지 않았다.

## 후속 전체 점검 — 회전 출력과 화면 STOP

수동 출력·복구·화면 종료, 카메라/조명 취소, 설정 및 이미지 저장, 캐리어 작업 결과 인계 경로를 추가로 대조했다. 다음 문제를 수정 전 테스트로 재현하고 고쳤다.

- Placement 회전: 티칭 버튼의 사전 확인 이후 상승 신호가 사라져도 회전 출력이 켜졌다. `PcbPlacementHandler.SetRotatedAsync`에서 기존 조건인 리프트 Up·이송 Z 정지를 출력 직전에 확인한다. 자동 시퀀스도 같은 메서드를 사용하며 정상 직접 인계·압착 재개를 검증했다.
- 메인 화면·축 진단창 STOP: 정지 출력 실패가 처리되지 않은 UI 예외로 전파됐다. 기존 `CommandShutdown.StopAsync`로 장치 STOP과 화면 명령 취소·종료를 끝까지 처리한다. 첫 알람이 없으면 `StopFailed`에 원인을 기록하고, 이미 알람이 있으면 첫 원인을 유지하며 추가 실패를 로그에 남긴다. STOP HOME도 같은 STOP 명령에 연결했다. STOP은 종료 대기 중에도 다시 누를 수 있다.
- 수동 컨베이어 STOP: `RunCommand.Cancel`의 모터 OFF 실패로 후속 준비/배출 완료 신호 해제가 생략됐다. 명시적인 컨베이어 정지와 명령 취소를 기존 종료 처리로 연결했다. 메인·NG 두 컨베이어 모두 실패한 모터 출력을 성공으로 표시하지 않으며 나머지 신호는 정리한다.
- 조그 해제·티칭 유닛 변경: 드라이버 STOP 콜백의 실패가 선택 변경/버튼 이벤트 밖으로 전파됐다. 장치 오류를 정지 실패 알람으로 남기고 취소 수명을 정리한다. 화면 비활성화·앱 종료에서는 정지 미확인 오류를 상위 종료 처리에 계속 전달한다.

새 감시 루프·동작 상태 캐시·범용 명령 프레임워크는 추가하지 않았다. 하위 장치의 실제 정지 확인과 실패 전파, 작업 소유권, 최초 알람 보존을 유지한다.

이 후속 점검의 직접 관련 Virtual 테스트는 중복 제외 **36개 통과**: 회전·인계 관련 9개, 화면 STOP 및 기존 종료 회귀 14개, 수동 컨베이어 8개, 조그 취소 및 수정 재확인 10개, 기존 WPF 화면 통합 테스트 1개에서 중복 7개를 제외하고, 창 종료 시 드라이버 정지 실패를 상위로 전달하는 1개를 추가 확인했다. WPF 테스트는 가상 장치와 별도 테스트 Application을 사용하며 `IBTM.App`이나 실장비 SDK를 시작하지 않는다. 전체 MachineFlow는 실행하지 않았다.

최종 대조에서는 최초 알람/추가 정지 실패의 구분, 취소 후 작업 정리, HS1 감지 후 추가 밀기 시간, 직접 인계의 세 조건, 체결 결과의 캐리어·볼트 귀속, NG 셔틀 복귀 이력, 이미지와 설정 저장을 다시 확인했다. 이번에 재현한 소스 결함은 모두 수정했다. 실제 장비의 정지 응답·센서 시점·회전 간섭 여유·카메라 해상도는 현장 피드백으로 확인해야 하며, 가상 검증 결과로 물리 동작의 적합성을 확정하지 않는다.

## 추가 점검 — ADC 진단창의 실제 상태 확인

자동 체결의 상태 확인과 별도로 연결된 ADC 진단창 버튼을 대조했다. 다음 두 문제는 가상 컨트롤러와 실제 WPF 버튼 이벤트로 수정 전 재현했다.

- STOP: 창 밖에서 시작한 모터에 STOP 레지스터 쓰기 응답이 오면, RUN이 계속 켜져 있어도 화면에 `Stopped`가 표시됐다. `AdcBoltHead.StopAsync`에 기존 STOP 전송·RUN OFF 확인을 모아 자동 체결의 종료와 진단창이 함께 사용한다. 설정된 응답 제한 시간 동안 실제 정지를 확인하며, 반복 STOP이나 취소로 이 확인을 생략하지 않는다. RUN이 꺼지지 않으면 정지 미확인 오류를 표시한다. 일반 통신 작업 취소도 더 이상 모터의 정지 완료로 표시하지 않는다.
- 프리셋 선택: 레지스터 쓰기 응답만으로 `Preset 7 selected`를 표시했고, 실제 컨트롤러 값이 3에 남아 있어도 성공으로 보였다. 진단창이 기존 `AdcBoltHead.SelectPresetAsync`를 사용해 정지·준비 상태와 프리셋 읽기 결과를 확인하도록 연결했다. 실패 후 정상 설정으로 재시도하는 경로도 확인했다.

이번 추가 점검의 직접 관련 Virtual 테스트는 중복 제외 **10개 통과**: 기존 ADC 상태·중단 결과 소유권 테스트 9개와 기존 WPF 통합 테스트 1개. WPF 테스트에 RUN OFF 지연·미확인·반복 STOP, 프리셋 적용 실패·재시도 검증을 추가했다. 프리셋 수정 후에는 해당 WPF 테스트만 다시 실행했다. 실장비 앱, 네이티브 장치 API, 전체 MachineFlow는 실행하지 않았다. 실제 ADC의 상태 갱신 시간은 현장 확인 대상이다.

## 후속 점검 — 정지 실패 시 감시·알람·명령 수명

중단된 소재 작업, 컨베이어 안착·배출, NG 복귀, 수동 조작 후 자동 운전, 입력 감시의 정지 경로를 대조했다. 다음 세 문제를 수정 전 가상 I/O로 재현했다.

- 입력 감시 종료: 비상정지 또는 AUTO 전환에서 모터 OFF 쓰기가 실패하면 `OnInputChanged` 밖으로 `AggregateException`이 전파됐다. 입력 감시가 영구 종료되어 이후 센서 변화와 RESET을 사용할 수 없었다. `StopAndReportFailure`가 기존 STOP을 실행하고 장치 정지 오류를 알람에 기록하도록 연결했다. 안전 입력, 축 인터록, I/O 장애에서 같은 처리를 사용하며, 다른 장치의 STOP은 끝까지 시도한다. 알람 통지의 취소 콜백에서 오류가 발생해도 나머지 장치 STOP을 생략하지 않는다.
- 비상정지 원인 덮어쓰기: 수동 컨베이어 작업의 비동기 정리가 늦게 끝나거나 수동 STOP을 다시 누르면, 기존 비상정지 알람을 I/O 통신 알람으로 바꿨다. 최초 알람을 유지하고 추가 실패를 상세 또는 로그에 기록한다. 정리 작업이 모두 끝난 시점과 STOP 재시도 이후를 검사했다.
- 자동 종료 예외 전파: 자동 운전의 마지막 `StopRunOutputs` 실패가 `StartAsync` 밖으로 전파되어 화면 START 명령까지 실패했다. 자동 종료에도 같은 정지 오류 처리를 연결했다. 장치 오류는 알람으로 남기고 명령이 정리되며, 프로그래밍 오류는 장치 오류로 숨기지 않는다.

직접 관련 Virtual 테스트는 중복 제외 **29개 통과**. 새 회귀 검증 4개는 실제 입력 스캔에서 비상정지·AUTO 전환을 발생시키며, 정지 실패 후 다음 스캔·입력 복귀·수동 재정지·RESET 또는 자동 명령 종료를 확인한다. 기존 검증 25개는 비상정지 우선 처리, 다른 장치 STOP 시도, 수동 컨베이어 정리, 축 인터록, 모드·서보 상실, 자동 운전 피드백과 감시 자체의 프로그래밍 오류를 다룬다. 전체 MachineFlow와 실장비 앱/SDK는 실행하지 않았다.

실패한 모터 출력은 테스트에서도 ON으로 남아 있음을 확인한다. 감시가 살아 있다는 이유로 정지 성공이나 재가동 가능으로 간주하지 않으며, 장치 오류 제거 후 명시적인 정지와 RESET을 확인했다. 실제 모터 정지 응답과 센서 시점은 현장 검증 대상이다.

## 연속 점검 — 취소를 요청한 감시와 장치 작업의 오류 소유권

AJIN 이동·원점복귀와 메인·NG 컨베이어의 취소 콜백에서 첫 STOP 쓰기를 실패시키고, 후속 정리의 STOP은 성공시키는 조건을 재현했다. 기존에는 STOP 오류가 취소를 요청한 입력 감시·버튼으로 전파되고, 장치 작업에는 단순 취소만 남았다.

각 작업의 이름 있는 `StopOnCancellation`에서 즉시 STOP을 시도하되 실패는 해당 작업이 수집한다. 취소 등록을 해제하며 진행 중인 콜백 종료를 확인한 뒤 작업 오류·STOP 오류를 함께 전달한다. AJIN은 실제 정지 피드백 대기와 마지막 위치 읽기를 유지하며, 그 실패도 보존한다. 컨베이어는 나머지 핸드셰이크 출력을 계속 정리한다. 범용 취소 프레임워크나 추가 감시 루프는 도입하지 않았다.

상위 수동 명령도 두 조건을 추가 재현했다. 비상정지 알람 이후 도착한 장치 오류가 버려지는 문제, 수동 작업 실패 후 STOP 출력 오류가 화면 명령 밖으로 전파되는 문제다. 수동 명령을 기존 `StopAndReportFailure`에 연결하여 첫 알람을 유지하고 추가 실패를 기록하며, 가능한 나머지 장치 정지를 끝까지 시도한다.

직접 관련 검증은 중복 제외 **29개 통과**: 네이티브 선언 없는 AJIN SDK 대역 검증 4개, 수동 오류·티칭 검증 12개, 컨베이어 취소·입력 감시 검증 13개. 기존 프로그래밍 오류 전파, 다른 출력 정지 시도, 비상정지 이후 감시 지속과 취소 수명 정리를 함께 확인했다. 전체 MachineFlow나 실제 장비 API는 실행하지 않았다. 원점복귀와 복구 명령의 상위 오류 처리 검토는 계속 진행한다.

## 연속 점검 — 원점복귀와 Repeat의 늦은 오류 응답

- 전체 원점복귀: 비상정지 처리 후 늦게 도착한 장치 오류가 `HomeFailed`로 첫 알람을 덮어썼다. 기존 알람을 유지하고 추가 오류를 기록한다. 취소된 원점복귀가 `false`를 반환하는 경우도 새 원점 실패로 바꾸지 않는다. 기존 원점복귀 대역에 종료 응답 대기만 추가하여 두 경우를 확인했다.
- AJIN XY 원점복귀: X의 원점 상태 읽기 오류 후 Y의 STOP까지 실패하면 `await Task.WhenAll`이 첫 오류만 전달했다. 두 축 작업의 예외를 함께 전달하도록 변경했고 SDK 대역으로 재현·검증했다.
- Repeat NG 복귀: 셔틀 동작 실패 뒤 NG 컨베이어 STOP이 실패하면 원래 동작 오류를 잃었다. 동작·정리 오류를 함께 보존하며, 비상정지 이후 도착한 오류는 첫 알람에 추가 기록한다. 중단된 복귀 단계를 테스트에서 지정하고 실제 START 명령으로 해당 단계만 실행했다.

추가 직접 검증은 **28개 통과**: 원점복귀·실린더 정지 13개, AJIN 동시 원점 오류 1개, Repeat·이송 14개. 앞 절의 AJIN 4개는 변경 후 다시 통과했으며 중복 집계하지 않는다. 이번 연속 점검 누계는 **57개**다. 전체 MachineFlow와 실제 장비 API는 실행하지 않았다.

기존 `MotionAlarmBlocksHomeAndStopsAllHomingAxes`는 첫 묶음 실행에서 동시 원점 시작 대기 제한 2초를 한 번 초과했다. 해당 테스트와 같은 13개 묶음 재실행은 통과했으며, 재발 시 완료 여부·시작 허용·차단 사유·알람을 확인할 수 있도록 실패 메시지를 보강했다. 이 일회성 대기 실패의 원인은 확정하지 않았다.

## 연속 점검 — 티칭 입력과 실제 좌표

검사 미리보기·자동 검사에서 같은 이진화 계산과 볼트별 임계값·합격 비율을 사용함을 대조했다. 줄자 보정은 양쪽 히트싱크 좌표를 계산하며 촬영 XY와 ROI를 유지한다. 해상도는 화면에서 읽기 전용으로 표시하고 줄자 적용으로 변경한다. 이 계산 경로는 변경하지 않았다.

볼트 PCB/IPM 프리셋 입력 세 곳을 기존 `RecipeInputs` 검증 그룹에 연결했다. 숫자로 변환할 수 없는 입력이 저장 버튼의 기존 검증에 포함되도록 한 XAML 변경이며, Virtual 앱 빌드만 수행했다. 경고·오류 0개이며 별도 UI 테스트는 추가하지 않았다.

AJIN 위치 읽기에서는 SDK가 성공 코드를 반환해도 계산된 좌표가 NaN/무한대이면 정상 위치로 표시되고 있었다. SDK 대역의 NaN과 단위 변환 오버플로 두 조건으로 재현했다. 이제 위치를 미확정으로 노출하고 읽기 오류를 전달하여 티칭·XY 이동 계산에 사용하지 않는다. 정상인 다른 축의 위치는 계속 표시한다. 실제 장비에서 이 반환값이 발생했다고 판단한 것은 아니다.

직접 관련 SDK 대역 검증 5개가 통과했다. 새 좌표 검증 2개와 기존 진단 읽기 1개를 추가 집계하고, 앞서 실행한 동작·정지 오류 보존 2개를 제외한 연속 점검 누계는 **60개**다.

## 연속 점검 — 종료 시 실제 정지 확인

앱 소유의 이동 작업이 없는 상태에서 비활성 축이 이동 중이거나 읽기 불가여도 `MachineController.ShutdownAsync`가 성공했다. 모션 대역으로 두 경우를 재현했다. 종료는 이제 기존 명령·장치 정리를 모두 기다린 뒤 구성된 각 축의 현재 `InMotion`을 한 번 읽고, 이동 중·읽기 실패를 정지 미확정 오류로 전달한다. 오류가 있어도 수집 루프는 끝까지 정리한다. 별도 감시 루프, 추가 이동/초기화 명령, 동작 상태 캐시는 추가하지 않았다.

종료 재시도는 이미 끝난 화면/수집 캐시가 아니라 현재 하드웨어를 다시 읽는다. 해당 피드백이 정상 정지로 돌아온 뒤에는 종료 확인이 통과한다. 앱 밖의 이동을 취소할 소프트웨어 작업이 없다는 이유로 정지 성공을 표시하지 않는다. 실제 장비에서 읽을 수 없는 비활성 축도 기존 종료 미확정 안내의 대상이 된다.

직접 관련 Virtual 검증 **11개 통과**: 현재 정지/읽기 불가 2개, 마지막 모션 피드백 대기 2개, STOP·종료 오류 보존 2개, 감시 자체 오류 2개, I/O 수집 수명 1개, 종료 중 설정 잠금 1개, 기존 WPF 창/명령 통합 1개. WPF 검증은 이 종료 변경의 회귀 확인으로 실행했으며 실장비 앱이나 SDK를 사용하지 않았다. 연속 점검 누계는 **71개**다.

## 연속 점검 — 병렬 원점복귀의 후속 오류와 실제 도착 좌표

플레이스먼트 원점복귀 실패로 전체 취소가 걸린 뒤 체결 유닛에서 정지 오류가 반환되면, `RunHomeStepAsync`가 취소 여부 때문에 두 번째 오류를 기록하지 않았다. 두 유닛의 응답 순서를 제어하는 대역으로 재현했다. 실제 장치 오류는 취소 이후에도 기존 알람의 상세/로그에 남긴다. 일반 취소는 오류로 추가하지 않는다. 직접 관련 원점복귀 검증 10개가 통과했고, 새 회귀 검증은 취소 토큰을 확인한 뒤 두 번째 오류를 반환한다.

AJIN의 위치 이동은 정지·InPosition만 확인하여 실제 좌표가 목표에 못 미쳐도 성공했다. Z가 이동 높이에 도착하지 않았는데 X 명령이 나가는 경우와, XY 이동에서 Y만 미도착한 경우를 SDK 대역으로 재현했다. 이제 기존 `RunMoveAsync`에서 위치 명령에 한해 이동 종료 후 각 축의 실제 좌표를 목표와 대조한다. 기존 위치 허용차 0.05 mm를 사용하며, 미도착은 축 번호·목표·현재 좌표가 포함된 모션 오류로 전달하고 기존 STOP/정리 경로를 실행한다. 후속 XY 이동·촬영·체결 단계로 성공을 반환하지 않는다. 조그와 리미트 탐색은 목표 좌표가 없는 명령이므로 기존 피드백 완료 조건을 유지한다.

도착 확인을 장치의 위치 명령 처리에 모아 유닛별 검사나 추가 감시 루프를 만들지 않았다. 직접 관련 SDK 대역 7개와 Virtual 15개가 통과했다. 정지·취소 오류 보존, 정상 XY 도착, Z 선행 이동, 중단된 공급 진입, 기존 원점복귀/정지 피드백 검증을 포함한다. 이번 구간의 새로 실행한 검증을 중복 제외하면 연속 점검 누계는 **90개**다. 실제 축의 InPosition/엔코더 오차와 정지 응답은 현장 검증 대상이다.

## 연속 점검 — 원점이 없는 좌표의 티칭 저장

## 추가 재검증 — 명령 시작 조건과 상태 통지의 읽기 오류

앞선 검토 이후 실제 오류 주입으로 다음 누락을 추가 확인했다. 위의 “추가 결함을 찾지 못했다”는 판단은 이 경로의 오류 처리까지 확인한 결과가 아니었다.

- 전체 START/HOME: 최초 `StartBlock`/`CanHome` 조회가 try 밖에 있어, 현재 SDK 상태 읽기의 IOException이 알람 없이 명령 밖으로 전달됐다. 개별 원점복귀는 이미 처리하던 오류였다. 이제 두 전체 명령도 예상한 장치 읽기 오류를 기존 정지·알람 경로에서 처리하고 동작을 시작하지 않는다.
- 실린더 전체 상승: 최초 허용 조건과 실행권 확보 후 재확인에서 캐리어 입력 읽기가 실패하면 같은 누락이 발생했다. 명령 진입과 상태 변경 통지에서 I/O 오류를 처리하며, 동작 전 실패하면 실린더 출력을 내보내지 않는다. 취소된 작업은 조건을 다시 읽지 않아 오류 처리 중 통지가 반복 진입하지 않는다.
- HOME 중 상태 변경: `HomeBlock`의 입력 읽기가 기존 모션 읽기용 try 밖에 있었다. 원점복귀 중 외부에서 상태 갱신을 통지하면 읽기 오류가 통지 호출자에게 전달됐다. 기존 try 범위에 조건 읽기를 포함해 작업을 취소하고 원인을 남긴다. 이미 발생한 알람은 유지한다.

기존 `MotionAlarmBlocksHomeAndStopsAllHomingAxes`의 원점 시작 대기 실패도 한 번 재발했다. 실패 당시 HOME Task는 완료됐고 알람은 없었다. 이 테스트는 준비 이동 Task가 끝나자마자 HOME을 호출했지만, 실행 가능 여부는 감시가 읽은 이동 상태도 사용한다. 준비 이동의 정지 피드백을 반영해 `CanHome`이 참이 된 뒤 시작하도록 테스트 준비 순서를 수정했고 같은 7개 묶음이 통과했다. 운전 허용 조건이나 정지 검증을 완화하지 않았다.

이번 변경은 기존 명령과 통지 처리 범위 안에서 끝냈다. 새로운 감시 루프·상태 캐시·제어 계층은 추가하지 않았다. 직접 인계, HS1 감지 후 추가 밀기, 밝은 영역 비율 검사와 볼트별 설정의 운전 조건은 변경하지 않았다.

## 2026-09-15 — PCB 공급 Ready 완료 시점 정정

사용자가 Front 1 Ready는 PCB를 모두 집은 뒤 끄는 신호라고 확정했다. 이전 코드는 캐리어 Available ON 직후 Ready를 끄고, PCB2 확인 뒤 다시 켰다. 가상 상위 설비와 테스트도 같은 잘못된 신호 순서를 전제로 했다.

Ready는 PCB1·PCB2 처리 동안 ON을 유지하고, 마지막 슬롯 확인/PCB 확보 후 Supply가 Rotation Z로 돌아오면 OFF한다. PCB2의 Placement 인계 완료는 기다리지 않는다. 기존의 빈 슬롯 건너뛰기는 유지한다. Available OFF 후 실행 중인 공급 루프가 Ready를 다시 ON해 다음 캐리어를 받는다. 새 단계나 물리 상태 캐시는 추가하지 않았다.

전체 STOP·알람·공급 루프 종료는 `PcbSupplyHandler.StopUpstream`에서 현재 Available을 확인한다. 캐리어가 있으면 기존 Ready를 유지하고, 캐리어가 없을 때만 대기 중 Ready를 끈다. 읽기 실패는 전달하고 Ready를 임의로 끄지 않는다. 이 변경은 픽업 도중 정지를 작업 완료 신호로 보내지 않기 위한 것이다. 다른 모터·피더의 정지와 원래 오류/정리 오류 보존은 유지했다.

가상 상위 설비도 Ready ON으로 입고, Ready OFF로 현재 캐리어 이탈, 다음 Ready ON으로 다음 입고를 수행하도록 바꿨다. 기존 슬롯 이력 검증 4개와 STOP/비상정지 검증 2개가 수정 전 실패하고 수정 후 통과했다. 직접 관련 Virtual 검증은 총 **23개 통과**: 슬롯 이력·완료 시점 4, STOP/비상정지 2, 입력 읽기 불가 1, 가상 입고/이탈/재입고 1, 픽업 중 캐리어 교체 1, 직접 인계 2, 전체 장치 정지 오류 보존 4, 작업/정리 오류 보존 8. 전체 MachineFlow와 실장비 앱·API는 실행하지 않았다. 실제 상위 설비와의 신호 타이밍 대조는 현장 확인 대상이다.

## 2026-09-15 — Supply XY 동시 이동

물리 버퍼 제거로 Supply도 XY 동시 이동이 가능하다는 사용자 결정을 반영했다. Supply의 장치 주입을 기존 `IXyMotion`으로 통일하고, 픽업·인계·티칭에서 `MoveToXYAsync`를 직접 호출한다. 운반 높이인 Rotation Z에 먼저 도착한 뒤 XY를 함께 이동하고, 픽업은 XY 도착 후 해당 PCB Z로 내려간다. 순차 X/Y 이동 helper와 인계 진입의 중복 Z 호출을 삭제했다. AJIN에는 이미 다축 위치 명령과 축별 도착 확인이 있어 드라이버를 추가하거나 변경하지 않았다.

인계 구역의 수동 Y 이동 제한을 제거해 Rotation Z에서 X/Y 조작을 허용한다. 수동 Z·회전 제한, Placement 간섭 조건, 인계 전 회전 확인은 유지했다. PCB 해제 후 Clear Z → X 단독 이탈과 원점복귀 순서도 유지한다. 티칭 안내와 현재 동작 문서를 함께 갱신했다.

기존 순차 이동 테스트를 실제 중간 XY 좌표와 운반 높이를 확인하도록 바꿔 수정 전 실패를 확인했다. 수정 후 관련 Virtual **10개**, AJIN SDK 대역 **2개**가 통과했다. XY 이동 중 정지하여 두 축 모두 목표에 못 미친 상태에서 인계를 재개하는 검증, 직접 인계의 세 입력·진공 상실·Supply 이탈, Ready 완료 시점과 캐리어 교체, 원점복귀 순서를 포함한다. 전체 MachineFlow나 실장비 앱·네이티브 API는 실행하지 않았다. 실제 대각 이동의 간섭과 정지 응답은 현장에서 확인한다.

## 2026-09-15 — 메모리 SMEMA 테스트 입력

사용자가 지정한 전단 2개와 후단 Ready에 각각 메모리 테스트 bool을 추가했다. Operation의 Front 1/Front 2 `TEST Available`, Rear `TEST Ready`에서 조작한다. 최종 동작은 티칭에서 TEST만, 자동에서 실제 SMEMA DI만 사용하는 것이다. 실제 DI 표시·센서 피드백·저장 설정은 바꾸지 않았다. 각 유닛의 기존 Changed 통지로 대기 중인 루프를 깨우며, 별도 감시나 I/O 대체 계층은 없다. STOP은 테스트 값을 유지하고 새 앱 실행에서는 모두 OFF다.

사용자의 후속 조건에 따라 티칭 접점 ON에서만 테스트 값 설정·사용을 허용한다. 저장 키는 기존 `InputIo.AutoMode`지만 실제 접점 ON이 수동/티칭이다. UI는 같은 입력으로 비활성화하고, 제어 코드도 현재 접점을 확인한다. 티칭 OFF를 받으면 세 값을 해제하여 다음 티칭 진입에서 자동 복원하지 않는다. 실제 SMEMA는 자동 모드에서도 정상 적용한다.

Front 1은 선택된 Available의 OFF→ON으로 다음 캐리어를 받는다. 티칭 중 실제 입력이 ON이어도 TEST OFF로 다음 캐리어 준비가 가능하다. 픽업 도중 TEST를 끄면 기존 취소/작업 귀속 처리도 적용된다. 티칭의 판단 코드에서는 상대 SMEMA 입력을 읽지 않으며, 선택기 피드백 오류와 일반 I/O 통신 오류는 유지한다.

자동 시퀀스의 전단 Ready 2개·후단 Available 쓰기는 `IIoService.SetAutomaticSmemaOutput`으로 모아 티칭에서는 실행하지 않는다. 초기화·티칭 전환 시 기존 STOP 경로가 SMEMA 출력을 OFF한다. OUTPUTS 창은 직접 `SetOutput`을 사용하므로 SMEMA도 수동 ON/OFF가 가능하다. 사용자 요청에 따라 이 창에는 새 제한을 넣지 않았고, 물리/Virtual I/O 드라이버도 변경하지 않았다.

관련 Virtual **25개 통과**: 메모리 신호로 Supply 두 슬롯 처리·다음 캐리어 1, 전단/후단 컨베이어 대기 해제·입력 선택·자동 출력 차단 2, 픽업 중 캐리어 교체의 실제/테스트 입력 2, 자동 모드의 입력 읽기 오류 1, 기존 슬롯/Ready 처리 4, 티칭 전환·설정 차단·실제/테스트 입력 선택 1, 상대 입력 미조회와 선택기 오류 1, STOP/비상정지의 공급 Ready 유지 2, 초기화/티칭 전환 출력 OFF·자동 출력 차단·직접 출력 허용 1, OUTPUTS 세 신호 직접 조작·지속 ON 1, 정상 자동 SMEMA 입출고 1, 작업/정리 오류 보존 8. XAML을 포함한 앱 의존성도 함께 컴파일했다. UI 전용 테스트·전체 MachineFlow·실장비 앱은 실행하지 않았다.

## 2026-09-15 — 인계 위치 독립 접근과 실린더 인수

사용자는 Placement 실린더 상승 상태에서 두 유닛이 간섭 없이 이동하도록 티칭하며, 어느 쪽이 먼저 도착해도 된다고 확정했다. Placement는 Supply 도착을 기다리지 않고 기존 인계 XYZ로 이동해 실린더 Up 상태로 대기한다. Supply도 Placement의 좌표 도착을 기다리지 않는다. 공유 영역에서는 실제 Handler Up/Down 쌍으로 상승을 확인하며, 기존 Z 기준 진입 판단은 제거했다. 수평 이동용 Buffer Entry Z 설정은 유지한다.

양쪽 인계 좌표 도착·정지와 Supply PCB 확보가 확인되면 Placement는 축 이동 없이 실린더만 내려서 인수한다. PCB 감지·진공·그리퍼 닫힘을 모두 확인한 뒤 Supply가 해제하고, Placement는 Supply 이탈 후 운반한다. 기존 인계 좌표·출구 동작·중간 정지 복구를 유지하고 별도 대기 좌표나 순서 플래그는 추가하지 않았다.

## 2026-09-15 — Placement 이동·회전·인계 Z 통합

사용자 결정에 따라 Placement의 `BufferHandoffPosition.Z`를 이동·회전·인수 공통 높이로 사용한다. `BufferEntryZ`와 별도 Approach Z 티칭 항목, 인계 XY 도착 후 Z를 내리는 상태·호출을 제거했다. 기존 파일의 인계 Z는 그대로 사용하며, 옛 `BufferEntryZ`는 읽을 때 무시하고 다음 저장에서는 제외한다. 공통 높이 이동 버튼은 `Handoff / Travel Z`로 표시한다. Z 티칭값은 공통 Z와 히트싱크 1·2 안착 Z의 세 개다.

실린더 상승 후 공통 Z에서 회전·XY 접근하고, 인계 시에는 실린더만 내린다. 기존 XYZ 인계 티칭의 적용·저장 방식과 실제 정지·홈·실린더 피드백 확인을 유지했다. 테스트용 Placement 모션도 실제 주입과 같은 공통 Z를 사용하도록 바꿨다.

관련 Virtual **11개 통과**: 두 도착 순서에서 회전·접근·인수 중 Z 유지 2, 옛 설정 로드/저장 1, 티칭 항목과 설정 반영 1, XYZ 홈 확인·공통 Z 적용/저장 1, Z 원점복귀 후 공통 높이에서 XY 홈 2, 연속 인계·안착 대상 유지 1, 세 신호 확인·Supply 이탈 1, 해제 중 진공 상실 1, IPM과 수평 이동 조건 1. 전체 MachineFlow와 실장비 앱은 실행하지 않았다.

## 2026-09-16 — Supply Clear Z 제거와 다음 PCB 픽업 XY 복귀

사용자가 인계 후 Clear Z 하강을 없애고, Placement 실린더가 Up인 상태에서 Supply를 다음 PCB 픽업 XY로 복귀시키기로 확정했다. PCB1 인계 후에는 PCB2 픽업 X와 공통 Carrier Y, PCB2 인계 후에는 다음 캐리어의 PCB1 픽업 X와 Carrier Y로 돌아간다. 기존 슬롯 이력으로 목적지를 선택하며 별도 복귀 좌표·진행 플래그는 추가하지 않았다.

Supply는 기존처럼 Placement의 PCB 감지·진공·그리퍼 닫힘을 확인하고 IPM 고정 실린더와 그리퍼를 차례로 해제한다. 두 후퇴 센서 쌍이 모두 완료를 확인한 뒤 Placement가 XYZ를 유지하며 메인 실린더만 올린다. Supply는 실제 Up ON·Down OFF 확인 후 Rotation Z에서 XY를 동시에 복귀한다. Placement는 Supply가 공유 영역을 벗어난 뒤 축을 이동한다. 공유 영역에서 Supply가 수평 이동하는 동안 Placement의 상승 확인을 잃으면 기존 간섭 감시가 정지·알람을 처리한다.

Clear Z 설정·티칭 항목과 전용 X 단독 이동 API를 삭제했다. 옛 JSON의 `BufferClearZ`는 무시하고 다음 저장에서 제외한다. Supply의 Z는 공통 Rotation Z와 PCB1·PCB2 픽업 Z의 세 개다. 화면에는 Supply 해제 대기와 Placement 상승 대기를 구분하고 현재 동작·설정 문서를 갱신했다.

직접 관련 Virtual 검증은 중복 제외 **10개 통과**: 세 인수 신호·해제 완료·모순 센서·상승 후 XY 복귀 1, 해제 중 진공 상실 1, 연속 인계에서 PCB2/다음 PCB1 복귀 좌표와 안착 대상 유지 1, XY 복귀 중 상승 확인 상실에 따른 정지·복구·재개 1, 인계 진입 중 정지/재개 1, 두 도착 순서의 실린더 인수 2, 공유 영역 간섭 1, 옛 설정 로드/저장 1, 티칭 항목 적용 1. 마지막에 보강한 테스트 2개만 다시 실행해 통과했다. 전체 MachineFlow와 실장비 앱·네이티브 API는 실행하지 않았다.

## 2026-09-16 — 화면 code-behind의 MVVM 전환

UI의 XAML code-behind 19개를 검토했다. 이미 ViewModel을 사용하던 작업 화면은 유지하고, 남아 있던 메인·ADC 진단·입력·출력·모션·로그·두 복구창의 화면 로직을 ViewModel과 명령 바인딩으로 옮겼다.

- ADC: `AdcProtocolViewModel`이 포트·속도·슬레이브·프리셋·레지스터 입력, 통신 명령, 역회전 Hold 취소, STOP 확인, 프레임 로그를 소유한다. 기존 `RunAdcProtocolAsync`/`RunBoltTestAsync` 진입과 실행 중 작업·취소 수명을 유지했다.
- 메인: 진단창 명령, 레시피 파일 선택, 전체 종료 대기를 `MainViewModel`로 옮겼다. 창 생성·재활성화·Owner 처리는 `DiagnosticWindows`에 둔다. 출력창 열기는 기존처럼 실제 선택기를 실행 시 다시 확인한다.
- 입력·출력: 목록·필터·새로고침은 각 WindowViewModel에 둔다. 실제 I/O와 기존 행 명령을 그대로 바인딩하며 OUTPUTS의 직접 출력 동작은 유지한다.
- 모션·로그·복구: 모션 상태 구독과 종료 대기는 `MotionWindowViewModel`, 로그 복사는 `LogWindowViewModel`, 복구 Apply는 각 복구 ViewModel의 명령으로 연결했다.

`.xaml.cs`에는 뷰 초기화·루트 DataContext·WPF 창 수명 이벤트와 종료 오류 대화상자 연결만 남겼다. `LogTextBox`의 텍스트 선택, 드롭다운 버튼의 템플릿 조작, `DialogResultBinding`의 창 결과 적용은 WPF 어댑터다. 앱의 DI 구성·시작/종료 진입점은 `App.xaml.cs`에 유지한다. 새 감시 타이머나 일반 이벤트 디스패처는 추가하지 않았다.
